# 需求管理流程与 PM 把关规范

> 本文件是 vedio-website（以下简称"本产品"）所有需求的**强制入口与决策制度**。
> 任何新功能、功能变更、缺陷修复引发的行为调整，都必须先经过本流程的产品经理（以下简称 PM）把关，再进入开发。
> 目标：用业内成熟的需求工程方法，保证"做正确的事"与"正确地做事"，避免需求口头化、范围蔓延与无验收交付。

## 1. 角色与职责（RACI）

本产品当前为个人/小团队项目，PM 可由需求提出者与开发者中的同一人兼任，但**角色动作必须独立履行**，不能以"自己开发"为由跳过把关动作。

| 角色 | 主要职责 | 关键交付物 |
| --- | --- | --- |
| 需求提出方（Reporter） | 描述场景、痛点与期望，提供复现路径或样例 | 原始需求（Issue/口头需求转写） |
| 产品经理（PM） | 澄清问题、判定价值、收敛范围、写需求卡、定优先级、定验收标准、评审变更 | 需求卡、优先级结论、验收标准、变更记录 |
| 开发（Dev） | 技术方案、工作量评估、按验收标准实现、自测 | 技术方案、代码、自测证据 |
| 验收方（QA/Owner） | 按验收标准逐条验收，决定是否放行 | 验收结论（通过/打回） |

RACI 约定：**PM 对"做不做、做什么、做到什么程度"负责（A），Dev 对"怎么实现"负责（A）**；PM 不替代 Dev 定技术方案，Dev 不擅自扩大或裁剪需求范围。

## 2. 需求生命周期（状态机）

所有需求用统一状态管理，状态流转必须留痕（在需求池表或 Issue 中更新）：

```
新建(New) → 评审中(In Review) → 已就绪(Ready) → 开发中(In Dev)
   → 待验收(In QA) → 已发布(Released)
                      └→ 打回(Reopened) → 回到 In Dev
任意非终态 → 已拒绝(Rejected) / 已搁置(On Hold)，须记录原因
已发布 → （后续迭代）变更走新需求，不原地改历史结论
```

状态门禁（不满足不得进入下一态）：

| 流转 | 门禁条件 |
| --- | --- |
| New → In Review | 已登记来源、场景、期望，PM 已认领 |
| In Review → Ready | 需求卡完整、验收标准可测、优先级已定、依赖与降级方案明确 |
| Ready → In Dev | Dev 已给出技术方案与影响面，PM 与 Dev 对范围达成一致 |
| In Dev → In QA | 自测通过，关联验收标准逐条有证据，构建/测试门禁全绿 |
| In QA → Released | 验收方按验收标准全部通过；不通过则 Reopened 并记录缺陷 |

## 3. 需求分级与类型

### 3.1 需求类型

| 类型 | 定义 | 是否必须走完整流程 |
| --- | --- | --- |
| 功能需求（Feature） | 新增能力或显著改变用户可感知行为 | 是 |
| 改进需求（Enhancement） | 对既有能力的体验/性能优化 | 是（可简化模板） |
| 缺陷修复（Bug） | 实际行为与既有验收标准/文档不符 | 轻量流程：复现+根因+回归用例 |
| 技术债/重构（Chore） | 不改变外部行为的内部调整 | 仅需说明动机与风险，免用户故事 |
| 文档（Docs） | 文档、注释、规范类变更 | 评审范围与受众即可 |

### 3.2 优先级模型：MoSCoW + 价值/成本二维校准

先按 MoSCoW 分四档，再用"用户价值 × 实现成本"校准，防止高成本低价值需求插队：

- **M（Must have，必须有）**：缺失则核心场景不成立，或涉及数据安全/资金/隐私。
- **S（Should have，应该有）**：重要但非阻塞，可短期绕行。
- **C（Could have，可以有）**：锦上添花，资源允许才做。
- **W（Won't have now，本期不做）**：明确记入需求池并说明原因，不等于永久否决。

校准规则（结合本产品"个人 NAS、资源受限、存储可选"的约束）：

1. 涉及**数据丢失、隐私泄露、未授权访问、分享链路安全**的，默认 Must。
2. 依赖 `DB_PATH`/`TMDB_API_KEY` 等可选能力的需求，**必须同时定义未启用时的降级形态**，否则不进入 Ready。
3. 高 CPU/磁盘开销（如转码、OCR、批量任务）需求，必须说明对低配 NAS 的影响与开关/上限。
4. 价值相近时，优先做"不增加新环境变量、不破坏零数据库默认"的方案。

## 4. 需求把关清单（Definition of Ready）

PM 在需求进入 Ready 前，必须逐项确认（DoR）。任一项不满足即打回补充：

- [ ] **问题陈述**：谁在什么场景下遇到什么问题，当前如何绕行？
- [ ] **目标与非目标**：本需求明确"不做什么"，划定范围边界。
- [ ] **用户故事**：符合"作为…我希望…以便…"格式，且可追溯到真实场景。
- [ ] **验收标准**：Given/When/Then 或可判定的清单，覆盖正常、边界、异常、降级四条路径。
- [ ] **依赖与开关**：依赖哪些可选能力（持久化/刮削/转码/ffmpeg/tesseract），未启用时如何降级。
- [ ] **影响面**：影响哪些页面、API、数据表、模板、静态资源（含 SW 缓存版本）。
- [ ] **兼容性**：是否影响既有 URL、API 契约、环境变量、数据库 schema（含迁移与回滚）。
- [ ] **优先级与类型**：已按第 3 节定级并写明理由。
- [ ] **度量**：上线后用什么信号判断有效（见 PRD 第 9 节指标体系）。

## 5. 验收标准编写规范（Definition of Done 输入）

- 一条验收标准只描述一个可判定行为，使用"给定/当/那么"或明确的"在 X 条件下，系统应 Y"。
- 必须覆盖四类路径：
  1. **正常路径**：主流程成功。
  2. **边界路径**：空库、单条、上限、临界值（如评分 1/5、窗口第 30 天）。
  3. **异常路径**：资源不存在（404）、参数非法（400）、未授权（401）、限流（429）。
  4. **降级路径**：可选能力未启用时（503 或 UI 隐藏）、外部依赖缺失时静默降级。
- 涉及前端渲染的，验收标准须能被 HTTP 测试断言（关键文案、data 属性、状态码、URL）。
- DoD（完成定义）统一要求：`go build ./... && go vet ./... && go test ./...` 全绿；模板经路由实际 render 验证；静态资源变更同步升级 `sw.js` 的 `CACHE_NAME` 并更新 PWA 测试断言；中文注释。

## 6. 变更控制

- 进入 In Dev 后，任何**范围/验收标准/数据契约**变更都属于需求变更，PM 须评估并更新需求卡与优先级，Dev 重新确认工作量，禁止"顺手加功能"。
- 紧急线上缺陷可先修复，但须在同一迭代内补齐需求卡与回归用例。
- 数据库 schema 变更必须：向后兼容迁移（`CREATE TABLE IF NOT EXISTS` / 增量列）、孤儿数据清理（Prune）、说明回滚方式；不得破坏未开启持久化的默认形态。

## 8. 本项目特有约束（PM 评审时一票否决项）

1. **零数据库默认**：不配置 `DB_PATH` 必须可独立运行；持久化功能未启用时 API 返回 503、UI 友好隐藏，不得报错刷屏。
2. **单二进制部署**：模板/静态资源走 `go:embed`，不得引入运行期外部前端构建依赖。
3. **NAS 资源约束**：重计算任务必须有开关、并发上限与降级；默认值面向低配设备。
4. **安全基线**：分享/认证/文件访问相关需求必须包含路径穿越防护、限流、签名/哈希存储等验收项。
5. **URL 正交与 SSR 一致性**：列表筛选参数保持可正交组合；页面为服务端渲染，关键状态需可被 HTTP 测试覆盖。
6. **中文交付**：注释、用户可见文案、提交信息使用中文；提交信息不使用"第 N 轮/期"等无业务含义表述。
